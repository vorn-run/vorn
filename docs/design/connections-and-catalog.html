Vorn · design note

What you have, and what you could have

The connectors page is answering two different questions in one list. A connector is a kind of thing. A connection is one you actually set up and now have to run, watch and fix. Mixing them means the thing you own shows up as a shopping result.

The problem

Azure DevOps appears three times

Once as a card in the grid, because it is a connector that exists. Again inside that card as “2 connected”, because you have some. And again below, twice, as the connections themselves. Three representations of one thing, none of which is the one you came for.

There is a quieter version of the same bug in the data. installedListings invents a catalog-shaped row for a package installed by name — a connection dressed up as something you could buy. It only exists because the connections list was not trusted to show it.

The change

Your connections lead. The catalog is a shelf you visit.

Connections are the working set: they run on a timer, they fail, they need a backfill. That is why you open this page. The catalog is where you go occasionally to add something new, so it sits below and starts collapsed — one line, not a wall.

The rules this follows

One noun per list

  1. Connections are instances; connectors are kinds. Never in the same list. If a row can be run, paused or deleted, it is a connection and belongs above.
  2. Group connections by connector, not by nothing. Two Azure DevOps connections nest under one heading that carries the icon and version. That is where “2 connections” belongs — next to them, not on a shopping card.
  3. The catalog shows everything, always. Including what you already use, because a second connection to the same connector is a normal thing to want. “In use” is a hint that stops you wondering, not a status.
  4. A package installed by name is a connection. installedListings goes away. It exists to give an unlisted package a card in the catalog, when the thing that actually exists is a connection to it — which the connections list can render from what it already has.
  5. Built-ins are connectors like any other. GitHub and Linear sit in the same catalog, under their own category. Nothing about the page needs to know which ones run in-process.

Empty and error states

The first run is the catalog

With no connections there is nothing to lead with, so the page opens on the catalog expanded, with one line above it saying what a connection is for. The same page, one section shorter — not a different screen with its own layout to maintain.

A connection that cannot sign in gets a red dot and Fix instead of Run, in the connections list where someone will actually see it. Today that lives in a separate banner at the top of the page, far from the row it is about.

Build order

Two steps

  1. Split the nouns. Group connections by connector, move the catalog below a disclosure, drop installedListings, and change “2 connected” to a quiet “in use”. The grid and panel already built do not change.
  2. Move status to the row. Fold the sign-in banner into the connection it concerns, with the action that fixes it.

Step one is the confusion. Step two is a separate irritation that becomes obvious once connections have a place of their own.
